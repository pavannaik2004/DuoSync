# Phase 5 — Admin and Organizers Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An admin can build, check, preview, activate and soft-delete themes and their 5 levels entirely in the browser, and grant the organizer role. Organizers publish public challenges that anyone can find in a filtered challenges list. Idle practice rooms expire (PRAC-4). PRD §11 Phase 5 gate: *a theme built only through the admin panel can be used in a public challenge.*

**Architecture:** Admin REST lives under `/api/admin` (`routes/adminRoutes.js`, behind `requirePlayer` + `requireRole('admin')`), with services `adminThemeService`, `adminLevelService`, `adminUserService` and `adminCatalog`. One pure function, `checkTheme(content)` in `services/themeCheck.js`, decides whether a theme is playable (ADMIN-4). It is used for activation, for every write to an active theme, and to list problems in the editor. The generators already take captions and table columns from each template's `fallback`, so the fallback doubles as the PRD's "clue templates" (D83). The level editor pre-fills it from a built-in example per mechanic. Client admin pages are lazy-loaded under `client/src/pages/admin/` (NFR-12).

**Tech Stack:** The Phase 4 stack (Node 22, Express 5, Mongoose 9, Socket.io, React 19, Vite 8, express-validator, express-rate-limit 8). No new dependencies.

**Spec:** `PRD Collaborative Digital Escape Room.md` (§2 roles, §5.3 CHAL-1/4, §5.9 PRAC, §5.10 ADMIN, §6.1 last paragraph, §8 NFR-3/5/6/12, §9.1 themes/leveltemplates, §9.2 admin routes, §11 Phase 5). Cross-phase rules are in `docs/superpowers/plans/2026-11-09-00-roadmap.md`. Before starting, read those, `DECISIONS.md` (D1–D82, plus D83–D96 added by this plan) and `CONTEXT.md`.

**PRD requirements covered:** ADMIN-1 to ADMIN-8; CHAL-1 public challenges (already enforced server-side; the list makes them reachable); CHAL-4; PRAC-1 to PRAC-3 (already done in Phases 2–3, re-checked by the gate) and PRAC-4; the acceptance checks "a non-admin gets 403 on every /api/admin route; a non-organizer can't create a public challenge" and "a guest can play practice mode but is refused when opening a challenge or team invite"; DECISIONS Q7; the deferred minors `seedThemes` overwrite never removing extra templates (moot, D94), `seedAdmin` untested, and the Dashboard tile that is a div.
**Not in this phase:** per-theme CSS for new style keys (an admin-built theme picks one of the 8 existing `STYLE_KEYS`; Phase 6 does the styling), new mechanics (they need code, §6.1), SCORE-6 and AUTH-7 (D78), restoring a soft-deleted theme.

## Decisions this plan adds (write them into DECISIONS.md in Task 13)

| # | Decision |
| --- | --- |
| D83 | **Fallback = clue templates.** Each level's `fallback` (fixed clue A, clue B, answer, reward, explanation and an optional `solution`) is what the PRD calls "clue templates": generators take captions, table columns and fixed paragraphs from it. Admins edit it as JSON. The level editor pre-fills `params` and `fallback` from a built-in example of the chosen mechanic (`GET /api/admin/catalog`) |
| D84 | **Activation check (ADMIN-4).** A theme is playable when: it has exactly 5 levels numbered 1–5; its name, both role names, a `styleKey` from `STYLE_KEYS` and a timer of 5–60 minutes are set; its fallback set passes `validateLevel` level by level; and 10 generated sets (seeds `check-0` … `check-9`) build without falling back. `checkTheme` lists every problem with the level it belongs to |
| D85 | **Active themes stay valid.** Every write to an active theme or its levels is checked on the would-be result first. If the result fails D84, the write is refused with 422 `THEME_INVALID` (details per problem) and nothing is saved. Deactivating is always allowed. To restructure a live theme (add, delete), deactivate it first |
| D86 | The slug is set at creation and never changes, because challenges and attempts keep `themeSlug`. Soft delete (ADMIN-7) sets `deletedAt` and `active: false`. A deleted theme keeps its slug reserved, stays readable in the admin panel, refuses writes with 409 `THEME_DELETED`, and cannot be restored |
| D87 | A new level is appended (order = level count + 1). A sixth gets 409 `THEME_FULL`. Deleting a level renumbers the rest 1…n. Reordering takes the full list of the theme's level ids in their new order, and is written in two phases (negative orders, then final) so the `{ themeId, order }` unique index never trips |
| D88 | Admin payloads may contain answers, fallbacks, solutions and pools: admins are trusted, and NFR-1 protects players in attempts. These payloads are served only under `/api/admin` |
| D89 | `/api/admin` accepts JSON bodies up to 200 KB (pools and fallbacks); every other route keeps 20 KB. `params`, `fallback` and `pools` must be plain JSON objects, nested at most 10 deep, with no key that starts with `$` or contains `.` (NFR-5) |
| D90 | ADMIN-6: admins grant or remove only `organizer`. `admin` stays seed-only (§2). Search `q` is 2–40 characters and matches part of the username or email, case-insensitively, with regex characters escaped. It returns at most 20 users, by username. A grant applies on the next request (D4); the client shows it after the next page load |
| D91 | CHAL-4 list: public challenges only, 20 per page. `status` is `upcoming` / `open` / `closed` / `all` (default `all`); `closed` means the window has ended, and each row shows its real status (`closing` while attempts still run). The `theme` filter is by slug. `upcoming` is sorted soonest first, everything else by newest start. Open to guests (§9.2 "Any"); opening a challenge still needs an account |
| D92 | PRAC-4: a practice room's `lastActivityAt` is set when the room is created, on each join, and when its last socket leaves. Every 60 s a sweep looks at rooms idle for 30 min with no connected socket. A room never played (`lobby`/`countdown`) is deleted with its messages. A finished room keeps its result, but its code is released (`$unset practiceCode`). Live games are left to the pause/grace rules (§7.6). Each delete or release repeats the idle filter, so a join that races the sweep survives |
| D93 | Q7 (NAT on event days): login and signup are limited per IP + email, and guest entry per IP + nickname, at `AUTH_RATE_LIMIT` (default 10/min). A per-IP ceiling, `AUTH_IP_RATE_LIMIT` (default 100/min), applies on top; it is never set below 10 × the per-key limit. **This reads NFR-6's "per IP" as "per IP and account". Confirm with the user at plan review** |
| D94 | `npm run seed` (`seedThemes({ overwrite: true })`) puts the 8 built-in themes back exactly as their modules define them: fields, active, not deleted, and the 5 templates by order. Admin edits, reorders, deletes and soft deletes of a built-in theme are undone. Orders are capped at 1–5, so a built-in theme can never keep an extra template, and the Phase 3 deferred minor is closed as moot. Seeding never touches themes whose slug is not a built-in one, so admin-made themes survive it. The README warns about this |
| D95 | `generateLevelSet` also returns `failure: { order, reason }` when it falls back (`null` otherwise), so the check and the preview can say why |
| D96 | Preview (ADMIN-5) works on any theme that isn't deleted, active or not, with an optional seed (default random). It saves nothing |

## Global Constraints

- **Workflow:** read `CONTEXT.md` before each task. Afterwards, append a dated log entry to it and record decisions in `DECISIONS.md`. Work on branch `phase-5-admin` (from `main`).
- **Commits:** no `Co-Authored-By` trailer and no mention of Claude (D20).

- **ADMIN-1 / NFR-3:** every `/api/admin/*` route answers 401 `AUTH_REQUIRED` without a token, 403 `GUEST_NOT_ALLOWED` for a guest and 403 `FORBIDDEN` for a player or organizer without `admin`. `tests/adminAuth.test.js` holds the full route table; Tasks 2–5 each add their routes to it.
- **NFR-1:** player-facing payloads are unchanged: attempts still go through `attemptView.js`, challenges through `challengeView.js`. The challenges list row carries no `levels`, `seed`, answers or fallbacks. Admin payloads (D88) are served only under `/api/admin`.
- **NFR-5:** every admin body field is validated with express-validator (`isString()`/`isObject()` before use). JSON fields go through `isPlainJson` (D89). Regex search input is escaped.
- **§6.1:** editing a theme or its levels never changes a challenge or attempt that already exists; they keep their saved levels and theme snapshot (D51).
- **NFR-12:** admin pages are `React.lazy` chunks. The main JS bundle grows by less than 5 KB gzip (it is 120.67 KB at the start of this phase). Opening a non-admin page never loads an admin chunk.
- **Pinned values:** exactly **5** levels per theme (ADMIN-4); a practice room expires after **30 minutes** without activity (PRAC-4); challenge list and user search page sizes **20**; `CHECK_SEEDS = 10`; auth limits **10/min** per key and **100/min** per IP by default (D93).
- Errors use `{ error: CODE, message, details? }` (D5). New codes: `THEME_NOT_FOUND` 404 (already exists), `LEVEL_NOT_FOUND` 404, `USER_NOT_FOUND` 404, `SLUG_TAKEN` 409, `THEME_DELETED` 409, `THEME_FULL` 409, `THEME_INVALID` 422.
- 360 px with no horizontal scroll; touch targets ≥ 44 px; status and check results shown as text, not colour alone (NFR-15, NFR-16). Challenge times are shown in local time (NFR-18).

## Review Focus

1. **A theme is deactivated or deleted while games use it.** A challenge created earlier still loads and plays its saved levels. A practice room in the lobby for that theme returns to the lobby with a message when someone readies up (D63), and no new challenge or room can pick the theme. Test in Task 2 (challenges and the theme list). The practice-lobby half is already pinned by `socketLobby.test.js` ("a theme deactivated after the room was made…"), and a soft delete takes the same `active: false` path.
2. **Reorder with a stale or wrong list** (an id missing, an id twice, an id from another theme). This gets 400 and nothing moves. A valid swap of levels 1 and 2 never hits the unique index. Test in Task 3.
3. **Hostile or malformed JSON** in `params`, `fallback` or `pools`: an array where an object belongs, a `$where` key, a dotted key, 12 levels of nesting. Each gets 400 `VALIDATION_ERROR` naming the field. Test in Task 3 (levels) and Task 2 (pools).
4. **The organizer role is removed between the page load and the submit.** The next public create gets 403 `PUBLIC_NEEDS_ORGANIZER`, because roles are read fresh on every request. Test in Task 5.
5. **The expiry sweep races a join.** A join that refreshes `lastActivityAt` after the sweep found the room but before it deleted it keeps the room. Test in Task 7.

  - `listThemes({ q, status }) → [{ id, slug, name, genre, active, deleted, levelCount, updatedAt }]`. `status` is `active` / `inactive` / `deleted` / `all`; by default every theme that isn't deleted. `q` matches part of the name or slug, case-insensitively and escaped. Sorted by name.
  - `getTheme(id) → ThemeDetail` = `{ theme: { id, slug, name, genre, story, roles, timerMinutes, styleKey, boardLabel, revealText, failText, pools, active, deletedAt, updatedAt }, levels: [{ id, order, title, mechanic, params, hint, rewardRule, timeEstimateSec, fallback }], problems: checkTheme(...) }`

  - `updateTheme(id, fields) → ThemeDetail`: if the result is active, `assertPlayable` runs first (D85)
  - `deleteTheme(id, now) → 204`
  - `loadDraft(id) → { theme, templates }` (404 `THEME_NOT_FOUND`; `{ writable: true }` adds 409 `THEME_DELETED`) and `assertPlayable(themeLike, templates)`, which throws `AppError(422, 'THEME_INVALID', 'This theme can't be active yet', details)` with `details = problems.map((p) => ({ field: p.order ? \`level ${p.order}\` : 'theme', message: p.message }))`. Task 3 uses both.
- Body rules (POST and PUT; PUT takes the full editable set and rejects `slug` with 400 on field `slug`, "The slug can't change"):
  - `slug` (POST only) matches `/^[a-z0-9]+(?:-[a-z0-9]+)*$/`, 3–40 characters
  - `name` 3–60 characters; `genre` ≤ 40; `story` ≤ 1200; `boardLabel` ≤ 30; `revealText`, `failText` ≤ 600; no control characters in any of them
  - `roles.A.name`, `roles.B.name` 2–30 characters; `roles.*.description` ≤ 200
  - `timerMinutes` an integer from 5 to 60; `styleKey` in `STYLE_KEYS`; `active` boolean (PUT only)
  - `pools`: `isPlainJson`; each value an array of at most 300 entries, each a string ≤ 120 characters or a plain object; pool names match `/^[A-Za-z][A-Za-z0-9]{0,39}$/`
